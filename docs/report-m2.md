# M2 Central Store & Ratification Dashboard Report

Results of implementing and live-testing M2 (backlog.md M2.1, M2.3, M2.5,
M2.6, M2.7, M2.8, M2.10) against real sensor traffic across both test VMs.
Built as a direct vertical slice — discover → aggregate → ratify → detect
drift → signal — rather than the full numbered story list: M2.2
(static-declaration seeding) and the expensive half of M2.4 (WHOIS-based
"newly-registered-domain") were deliberately left out as polish, not proof.
Two cheap risk annotations (direct-to-ip, shell-initiated) were kept since
the data was already available. mTLS, flagged as a recurring question in
`backlog.md`'s parking lot, was dropped here the same way it was for M1.6 —
plain HTTP, node identity carried by the `instance` field.

Environment: `rhel-9-2vcpu` running both `central` and one `sensor`
(loopback upload), `rhel-9-ebpf` running the second `sensor` (uploading to
`rhel-9-2vcpu`'s pod IP) — the same two-node setup proven in the M1 report.

## What was built

- **Ingestion** (`POST /events`) — same JSON shape `cmd/sensor` already emits.
- **Proposal builder** — groups by (fleet_identity, endpoint, port,
  protocol); tracks instance set, first/last seen, count, and the two risk
  annotations.
- **Git-backed decision store** — one JSON file per decision, a real
  `git commit` per ratification. No self-referential `version` field in the
  schema; a decision's version is the commit that touched it (`git log --
  <path>`), not something worth storing redundantly inside the file.
- **Review UI** (`GET /`) — server-rendered `html/template`, plain HTML
  forms, no JS framework. Recent-signals panel plus pending-proposals table
  grouped by workload.
- **Drift detector** — a fleet_identity with ≥1 ratified decision, contacted
  on a net-new undecided endpoint → `spec_deviation`. The drifted endpoint
  reappears in the pending queue automatically — this falls out of the same
  "is this decided yet?" check the proposal builder already does; no
  separate re-entry logic was needed.
- **Invariant pipeline** — `raw_socket` events → `invariant_violation`,
  always-on regardless of ratification, matching what M0/M1 actually built.
  The demo script's "`/bin/sh` spawned from a service" invariant was
  deliberately out of scope from M0 onward (other tools already cover
  process-ancestry detection) — the raw-socket invariant substitutes for
  that step of the demo.
- **`denied_endpoint_observed`** — falls out for free once decisions support
  both `allow` and `deny`; no separate code path was needed.
- **Signal stream** — JSON-lines file sink (`data/signals.jsonl`). No
  webhook delivery this pass; the file sink already proves the signal shape
  and detection logic, which is what was actually in question.

## Bugs found and fixed during live testing

Both were found only once real sensor JSON hit the central service — a
synthetic local smoke test (hand-written fake events) missed both, because
it used the string `"tcp"` for `protocol` in every test event and never
exercised the real numeric raw-socket wire values.

### `family` field type collision

`conn` events encode `family` as a string (`"ipv4"`/`"ipv6"`); `raw_socket`
events encode it as a number (the raw `socket(2)` domain, e.g. `17` for
`AF_PACKET`). The shared `RawEvent` struct originally declared `Family
int32`, which broke decoding conn events outright:
`json: cannot unmarshal string into Go struct field RawEvent.family of type
int32`. First live upload attempt from `rhel-9-2vcpu`'s sensor hit this
immediately.

### `protocol` field type collision (same class of bug)

Same story, different field: `conn` events encode `protocol` as a string
(`"tcp"`), `raw_socket` events encode it as a number. Fixed the `family`
bug, redeployed, and the *next* upload attempt hit the identical class of
error on `protocol`.

**Fix (both):** changed both fields to `any` in the shared decode struct,
with a typed `protocolStr()` accessor for the one place (`conn` event
handling — decision lookups, proposal grouping keys) that genuinely needs a
comparable string. `Family` didn't need an accessor; it's only ever
re-serialized into a signal's evidence map, never compared.

**Process note:** the uploader originally discarded the HTTP response body
on rejection, so the first symptom was just `"upload rejected" status=400`
with no reason. Fixed permanently (not just for debugging) to log the
response body on non-2xx — this is exactly the kind of thing that would
otherwise cost real debugging time in a less controlled setting.

## Demo scenario — verified live, end to end

1. Both nodes' sensors upload real discovery events to `central` — confirmed
   (§ M1's two-node report already proved the transport; this proved the
   central-side logic on top of it).
2. A real proposal (`example.com.` under `systemd:session`, generated by an
   actual `curl` in an SSH session) appears in the review queue.
3. Ratified via the real UI form — real `git commit` lands
   (`ff49b44 j.west: allow example.com.:443/tcp (systemd:session)`).
4. **Drift, cross-node:** `curl https://www.redhat.com` from `rhel-9-ebpf`
   (a *different* node than the one the decision was ratified against)
   produced `spec_deviation` signals correctly attributed to
   `"instance":"rhel-9-ebpf"` — direct confirmation that `fleet_identity`
   is genuinely instance-agnostic, not just superficially so. This is the
   cleanest evidence so far for the architecture's core claim ("500
   identical servers aggregate into one fleet identity").
5. **Deny:** ratifying the drifted `172.30.0.10:53` endpoint (the cluster
   DNS resolver — an organically-discovered undeclared dependency, exactly
   the kind of thing M2.2's static-declaration seeding would have
   pre-marked as infrastructure) as `deny`, then repeating that traffic from
   `rhel-9-ebpf`, produced `denied_endpoint_observed` — also correctly
   cross-node.
6. **Invariant:** a real `AF_PACKET`/`SOCK_RAW` socket created on
   `rhel-9-ebpf` produced `invariant_violation`, unconditional on
   ratification state, as designed.
7. Legitimate repeat traffic on an already-`allow`ed endpoint produced no
   signal — confirmed quiet, not just assumed.

## Outstanding items (not blockers, honest gaps)

1. **No webhook delivery** — file sink only. Fine for proving the detection
   logic; a real SIEM/SOAR integration would need this.
2. **M2.2 (static-declaration seeding) not built** — every proposal,
   including obvious infrastructure (DNS, NTP, package mirrors), currently
   requires the same manual ratification as application traffic. The
   cluster-DNS-resolver drift case in the demo above is a live illustration
   of exactly the noise this feature exists to pre-mark as "suggested:
   allow."
3. **"newly-registered-domain" risk annotation not built** — requires an
   external WHOIS/RDAP lookup; real scope, not a quick win like the other
   two annotations.
4. **In-memory proposal state does not survive a `central` restart.** Ratified
   decisions do (git-backed); pending proposals would need to be
   rediscovered from fresh traffic. Acceptable for a PoC — the property
   actually worth testing (node-side resilience) is M1's and already
   proven — but worth knowing before treating `central` as production-durable.
5. **Reviewer-minutes-per-workload was not measured.** The backlog's
   "ratifiable in minutes" claim — flagged in an earlier discussion as the
   single most commercially load-bearing unproven assumption in the whole
   project — was not tested against a realistic multi-workload queue in
   this pass. What was proven is that the *mechanism* (grouping, forms,
   git-backed ratification, drift detection) works correctly; whether the
   *experience* holds up at realistic scale is still open.

## Summary

The full backlog M2 demo scenario runs end to end on real sensor traffic
across two real nodes: discovery, grouping, ratification with a real git
commit, drift detection that correctly generalizes across node instances,
the deny path, and the one invariant this PoC actually built. Two real bugs
(the `family`/`protocol` type collisions) were found only by testing with
genuine sensor output rather than hand-written fake events — the same
lesson M0 and M1 already taught, reconfirmed. The core technical loop the
whole project exists to prove — ratify a spec, then catch deviation from it
— now has a working, live-tested implementation. What remains unproven is
the UX claim that actually matters commercially: whether ratification stays
fast at realistic scale, not whether the mechanism is correct.
